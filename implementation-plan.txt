# OCR Server Implementation Plan

## Objective

Update the existing `ocr-server` so that it reliably serves OCR requests from the `my-ocr-parser` frontend.

The server is already successfully processing:

* PDF invoices
* Passport images
* PAN images
* PaddleOCR extraction

Do not replace the existing OCR engine or processing pipeline.

The primary goal is to make the `/ocr` API a reliable frontend-consumable API, including proper CORS configuration, consistent JSON responses, error responses, and request logging.

---

# 1. Preserve Existing OCR Processing

Do NOT modify or replace the current PaddleOCR implementation unless required.

The current server is already successfully processing images such as:

```text
ANIKET-pass.png
ANIKET-pan.png
deshpande-back.png
deshpande-pan.png
```

The server is producing extracted fields such as:

```json
{
  "passport_number": "Y3647377",
  "surname": "GHOSH",
  "given_name": "ANIKET",
  "date_of_birth": "01/10/2000"
}
```

and:

```json
{
  "pan_number": "CUDPG6208B",
  "name": "ANIKET GHOSH",
  "father_name": "ASIM GHOSH",
  "date_of_birth": "13/12/1969"
}
```

Keep this extraction functionality intact.

---

# 2. Fix CORS

The frontend is running on a different origin from the OCR server.

Typical setup:

```text
my-ocr-parser
http://localhost:3000

        ↓

ocr-server
http://localhost:5000
```

Configure Flask CORS so browser requests from the frontend are allowed.

Install:

```bash
pip install flask-cors
```

Add:

```python
from flask_cors import CORS
```

Then configure:

```python
CORS(
    app,
    resources={
        r"/ocr": {
            "origins": [
                "http://localhost:3000",
                "http://127.0.0.1:3000"
            ]
        }
    }
)
```

If the project already has CORS configuration, modify the existing configuration instead of creating a second one.

---

# 3. Support Development Origins

During development, support both:

```text
http://localhost:3000
http://127.0.0.1:3000
```

Do not use:

```python
CORS(app, origins="*")
```

unless there is a specific reason.

The goal is to allow the local frontend while keeping the configuration explicit.

Make the allowed origins configurable through environment variables if practical.

For example:

```env
FRONTEND_ORIGINS=http://localhost:3000,http://127.0.0.1:3000
```

---

# 4. Standardize `/ocr` Response

The `/ocr` endpoint must always return valid JSON.

Successful response should have a predictable structure.

Use something similar to:

```json
{
  "success": true,
  "filename": "ANIKET-pass.png",
  "document_type": "PASSPORT_FRONT",
  "engine": "paddle",
  "processing_time": 44.86,
  "data": {
    "passport_number": "Y3647377",
    "surname": "GHOSH",
    "given_name": "ANIKET",
    "date_of_birth": "01/10/2000",
    "sex": "M",
    "place_of_birth": "BERHAMPORE, WEST BENGAL",
    "place_of_issue": "KOLKATA",
    "date_of_issue": "19/06/2024",
    "date_of_expiry": "18/06/2034"
  },
  "raw_text": "...",
  "message": "OCR completed successfully"
}
```

For PAN:

```json
{
  "success": true,
  "filename": "ANIKET-pan.png",
  "document_type": "PAN",
  "engine": "paddle",
  "processing_time": 34.64,
  "data": {
    "pan_number": "CUDPG6208B",
    "name": "ANIKET GHOSH",
    "father_name": "ASIM GHOSH",
    "date_of_birth": "01/10/2000"
  },
  "raw_text": "...",
  "message": "OCR completed successfully"
}
```

The exact existing field names should be preserved where possible.

---

# 5. Never Return HTML for API Errors

The frontend should never receive an unexpected Flask HTML error page from `/ocr`.

All expected API errors should return JSON.

Example:

```json
{
  "success": false,
  "error": {
    "code": "INVALID_FILE",
    "message": "Unsupported file type"
  }
}
```

Use appropriate HTTP status codes:

```text
400 → invalid request/file
413 → file too large
415 → unsupported file type
500 → server processing error
```

---

# 6. Handle Missing File

If the frontend sends:

```text
POST /ocr
```

without a file, return:

```json
{
  "success": false,
  "error": {
    "code": "FILE_REQUIRED",
    "message": "No file was provided"
  }
}
```

with:

```text
HTTP 400
```

Do not allow the request to reach the OCR engine.

---

# 7. Validate File Type

Continue supporting the formats already supported by the server:

```text
.png
.jpg
.jpeg
.webp
.bmp
.tif
.tiff
.pdf
```

Reject unsupported files cleanly.

Example:

```json
{
  "success": false,
  "error": {
    "code": "UNSUPPORTED_FILE_TYPE",
    "message": "Unsupported file type: .xyz"
  }
}
```

---

# 8. Preserve Document Type Detection

The server currently identifies documents such as:

```text
PASSPORT_FRONT
PAN
```

Keep this behavior.

The response should expose the detected type:

```json
"document_type": "PASSPORT_FRONT"
```

or:

```json
"document_type": "PAN"
```

This allows `my-ocr-parser` to understand what the OCR server returned without implementing its own document classification logic.

---

# 9. Return Extracted Fields Separately

Do not force the frontend to parse raw OCR text.

Bad:

```json
{
  "text": "INCOME TAX DEPARTMENT ... CUDPG6208B ..."
}
```

Instead return:

```json
{
  "data": {
    "pan_number": "CUDPG6208B",
    "name": "ANIKET GHOSH",
    "father_name": "ASIM GHOSH",
    "date_of_birth": "01/10/2000"
  }
}
```

Raw OCR text can still be included for debugging:

```json
"raw_text": "..."
```

---

The logs should show:

```text

...

```

This is useful for debugging OCR quality.

Do not remove these logs.

---

# 11. Add API Request/Response Logging

Add a concise API-level log around each `/ocr` request.

Example:

```text
[API] POST /ocr
[API] filename=ANIKET-pan.png
[API] content_type=image/png
[API] request_id=abc123
```

After processing:

```text
[API] request_id=abc123
[API] status=200
[API] document_type=PAN
[API] processing_time=34.64s
```

For failures:

```text
[API] request_id=abc123
[API] status=500
[API] error=OCR_PROCESSING_FAILED
```

Use a request ID so frontend and server logs can be correlated.

---

# 12. Add Health Endpoint

Add:

```text
GET /health
```

Response:

```json
{
  "status": "ok",
  "service": "ocr-server"
}
```

This allows `my-ocr-parser` to verify that the OCR server is reachable before starting a long OCR operation.

---

# 13. Add CORS Verification Endpoint

Optionally add:

```text
GET /health
```

and verify from the browser.

The response should include the appropriate:

```text
Access-Control-Allow-Origin
```

header when called from:

```text
http://localhost:3000
```

---

# 14. Do Not Change OCR Processing Time Yet

The current PaddleOCR processing can take tens of seconds.

For example, the server successfully processed:

```text
Passport: ~44.86s
PAN: ~34.64s
```

The frontend must therefore treat `/ocr` as a long-running request.

Do not introduce arbitrary frontend timeouts such as:

```text
10 seconds
20 seconds
30 seconds
```

unless the timeout is intentionally configured to exceed expected OCR processing time.

---

# 15. Make the API Response Available Only After OCR Completes

The `/ocr` request should behave synchronously:

```text
POST /ocr
      ↓
Receive image
      ↓
Run PaddleOCR
      ↓
Extract fields
      ↓
Build JSON response
      ↓
HTTP 200
```

The frontend should receive the extracted JSON directly from that request.

Do not write the result only to a server log or local file and expect the frontend to retrieve it separately.

---

# 16. Verify Multipart Upload

The frontend is expected to send the image using `multipart/form-data`.

The server should support something like:

```text
POST /ocr
Content-Type: multipart/form-data
```

with:

```text
file=<image>
```

Make sure the server reads the same field name expected by `my-ocr-parser`.

If the frontend currently sends:

```text
file
```

then preserve that.

Do not arbitrarily rename it to:

```text image
```

without updating the frontend.

# 20. Important: Do Not Modify the Existing Invoice Pipeline

The invoice pipeline is already working.

For example, the existing server successfully:

* receives the invoice
* extracts PDF text
* parses invoice fields
* validates arithmetic
* normalizes fields
* returns successful processing

Therefore this implementation should be **backward compatible**.

The new changes should primarily affect:

```text
API reliability
CORS
JSON response structure
Error handling
Logging
Health checking
```

Do not rewrite the invoice parser.

---

# 21. Acceptance Criteria

The implementation is complete when:

### API

* `/ocr` accepts image uploads.
* `/ocr` accepts PDFs.
* `/ocr` returns JSON.
* Successful OCR returns HTTP 200.
* Errors return JSON rather than HTML.
* Passport extraction returns structured passport fields.
* PAN extraction returns structured PAN fields.
* Existing invoice extraction continues working.

### Browser

From `http://localhost:3000`:

* `/ocr` can be called successfully.
* No CORS error occurs.
* No `Failed to fetch` occurs when the server is healthy.
* Frontend can read the JSON response.

### Debugging

Server logs clearly show:

```text
request ID
filename
document type
OCR engine
processing time
status
```

### Compatibility

Do not break:

* existing invoice processing
* PDF processing
* PaddleOCR
* existing dashboard
* existing OCR endpoints
* existing document types

---

# Final Principle

The OCR server is already doing the difficult part — **PaddleOCR is processing the documents and extracting the data successfully**.

The implementation should now make the server behave as a clean API:

```text
IMAGE
  ↓
OCR
  ↓
STRUCTURED JSON
  ↓
HTTP 200
  ↓
FRONTEND
```

The frontend should never have to read server logs to obtain OCR data.
