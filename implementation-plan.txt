IMPLEMENTATION PLAN — Add PDF Input Support

OBJECTIVE

Extend the existing OCR server so /api/v1/ocr accepts both:

- image files
- PDF files

Do NOT break the existing image OCR pipeline.

CURRENT PROBLEM

Uploading a PDF currently reaches the PIL image loader and fails with:

    cannot identify image file <tempfile.SpooledTemporaryFile>

This means the endpoint currently assumes every uploaded file is an image.

IMPLEMENTATION

1. Detect the uploaded file type before passing it to PIL.

Supported:

    Images:
      PNG
      JPG/JPEG
      WEBP
      TIFF
      BMP

    PDF:
      application/pdf
      .pdf

2. Keep the existing image path completely unchanged.

3. For PDF files:

    uploaded PDF
        ↓
    render each page to an image
        ↓
    pass each page through the EXISTING OCR pipeline
        ↓
    collect OCR results
        ↓
    return combined page results

4. Use PyMuPDF (`fitz`) for PDF rendering.

Install:

    .\venv\Scripts\python.exe -m pip install pymupdf

Do not require Poppler if PyMuPDF can handle the rendering directly.

5. Render PDF pages at a suitable DPI.

Start with approximately 200–250 DPI.

Do not unnecessarily render at extremely high resolution because OCR performance matters.

6. Each PDF page must go through the same preprocessing/OCR pipeline currently used for images.

Do NOT create a separate OCR implementation for PDFs.

The flow should effectively be:

    PDF page
       ↓
    PIL Image
       ↓
    existing adaptive OCR
       ↓
    existing document/parser logic

7. Return page-level results.

Use a structure similar to:

{
    "success": true,
    "file_type": "pdf",
    "pages": [
        {
            "page": 1,
            "document_type": "...",
            "text": "...",
            "fields": {...}
        },
        {
            "page": 2,
            "document_type": "...",
            "text": "...",
            "fields": {...}
        }
    ]
}

Preserve the existing response structure as much as possible for normal image uploads.

8. Do not modify:

    - Passport Front parser
    - Passport Back parser
    - PAN parser
    - adaptive preprocessing
    - MRZ authority logic
    - OCR candidate scoring
    - dashboard behavior

unless absolutely necessary to support page-level PDF results.

9. Add clear validation:

    - reject unsupported file types
    - handle empty PDFs
    - handle corrupted PDFs
    - handle password-protected PDFs gracefully
    - return a useful HTTP error instead of a Python traceback

10. Do not save uploaded PDFs permanently unless the existing application
    already requires that behavior.

Prefer processing PDF pages in memory.

TESTING

Test the existing image endpoint first:

    PNG
    JPG/JPEG

Expected:
    existing behavior unchanged.

Then test:

    1-page PDF
    multi-page PDF

Verify:

    page count
    OCR text per page
    extracted fields per page
    document classification per page

Also test a PDF containing:

    Passport Front
    Passport Back
    PAN

if available.

REGRESSION

Run:

    Passport Front regression
    Passport Back regression
    PAN regression
    full 20-image regression

Expected:

    0 document-type regressions
    0 field regressions

PERFORMANCE

Measure:

    image OCR time
    PDF page rendering time
    OCR time per PDF page
    total PDF processing time

Do not optimize prematurely.

IMPORTANT

The existing image OCR pipeline is working.

PDF support should be an INPUT/CONVERSION layer:

    PDF → page image → existing OCR pipeline

Do not rewrite the OCR engine or parsers to support PDFs directly.
